Rust七十二变（Rust 72 Changes）

附录8 Agent、技能与 MCP

给我一个撬棍，我能撬动一块石头；给我一个 USB-C 口，我能撬动整个生态。

Agent 负责「决定做什么」，Skill 负责「知道怎么做」，MCP 负责「连得上、够得着」。三者叠在一起，才是一个能干活的智能体。

一、先看一场「翻车」

你对 AI 说：「帮我把 invoice.pdf 里的表格填好，再整理成一页周报发给我。」

三种 AI，三种下场：

AI 形态会发生什么缺的是什么
纯聊天模型把它臆想出来的表格内容用文字打印给你，文件名、数字全靠猜看不见文件，动不了手
给了工具的大模型找到 PDF，但把「填表」理解成「在文件末尾追加一段文字」，格式全乱不知道这个领域的正确流程
配齐三件套的智能体调用 PDF 工具读出表单字段，按团队模板逐项填好，生成周报——

差别不在模型聪明程度，而在三样东西是否就位。这一附录就讲清它们：

  • Agent（智能体）：那个「一直转下去」的循环——观察、思考、调用工具、再看结果，直到活干完。
  • Skill（技能）：一份「岗位操作手册」，把某个领域的流程和经验打包成文件，用到时才翻开。
  • MCP（模型上下文协议）：一个「标准插座」，让智能体用同一套接口连上任意外部工具和数据源。

一张图先建立整体印象：

flowchart TB
    U[用户一句话需求] --> A

    subgraph A[Agent 智能体 · 决策循环]
        L[LLM 思考: 下一步做什么]
        O[观察工具返回结果]
        L --> O --> L
    end

    A -->|"按需加载 操作手册"| S[Skill 技能<br/>SKILL.md + 脚本 + 参考文档]
    A -->|"标准协议 调用工具"| C[MCP Client]

    C -->|JSON-RPC| M1[MCP Server: 文件系统]
    C -->|JSON-RPC| M2[MCP Server: 数据库]
    C -->|JSON-RPC| M3[MCP Server: 第三方 API]

    S -.->|"手册里写着 该调哪个工具"| A

三者不是一个递进关系，而是三个正交的维度：Agent 提供「意愿与循环」，Skill 提供「知识与方法」，MCP 提供「连接与动作」。少任何一个，都会退化成上表里的前两种翻车现场。

二、Agent：一个停不下来的循环

2.1 剥掉营销术语后剩下什么

把 Agent 拆到最小，它只是一个 while 循环：

把用户目标放进上下文 → 让模型输出「下一步动作」 → 执行动作拿到结果
→ 把结果塞回上下文 → 再问模型「下一步」 → …… → 模型说「完成了」→ 退出

这里有三个关键点，比任何框架名字都重要：

  1. 上下文窗口就是它的全部记忆。模型没有跨回合的「大脑」，每一次思考都只看得见窗口里现有的 token。工具结果、技能文档、历史对话，全都要塞进去才「存在」。
  2. 工具是它唯一的手脚。模型自己只能输出文字；要读写文件、查数据库、发请求，必须调用一个外部函数，并把结果读回来。
  3. 循环由模型自己决定何时结束。不是你写 for i in 0..10，而是模型每轮判断「目标达成了吗」。判断错了，就会像选项二那样瞎忙。

值得注意的一个转向：Anthropic 在复盘里把这件事概括成 「code is all you need」——Claude Code 表面是编程助手，本质是一个「恰好通过代码干活」的通用智能体。Bash 加文件系统，就是它的手脚（这也正是本仓库 src/SKILL.md 里那个 Rust Playground 技能的工作方式）。

2.2 用零依赖 Rust 写一个「玩具 Agent」

真正的 Agent 里，「思考」由大模型完成。为了看清循环本身，我们用一个确定性的 decide 函数冒充模型——它根据观察到的数字决定下一步动作。这段代码不依赖任何第三方 crate，可以直接丢进 Rust Playground 运行。

▶ 在 Rust Explorer 中运行
#[derive(Debug)]
enum Action {
    Call(String), // 调用一个工具
    Done(String), // 任务完成
}

// 冒充 LLM：真实实现里，这里是一次模型推理
fn decide(goal: i32, observed: i32) -> Action {
    if observed >= goal {
        Action::Done(format!("达标：{observed} ≥ {goal}"))
    } else {
        Action::Call("+1".to_string())
    }
}

// 冒充工具：真实实现里，这里可能是读写文件、查数据库、发 HTTP 请求
fn call_tool(name: &str, value: i32) -> i32 {
    match name {
        "+1" => value + 1,
        _ => value,
    }
}

fn agent_loop(goal: i32) -> String {
    let mut observed = 0; // 上下文窗口里的「当前状态」
    for turn in 1..=100 {
        // 1. 思考：把目标与观察结果交给模型，得到下一步动作
        let action = decide(goal, observed);
        println!("第 {turn:2} 轮 | 观察 = {observed:2} | 动作 = {action:?}");

        // 2. 行动 or 结束
        match action {
            Action::Call(tool) => {
                // 3. 把工具结果塞回上下文，进入下一轮
                observed = call_tool(&tool, observed);
            }
            Action::Done(msg) => return msg,
        }
    }
    "超过最大轮次，判定失败".to_string()
}

fn main() {
    println!("{}", agent_loop(5));
}

把 decide 换成一次真正的模型调用、把 call_tool 换成 MCP 客户端，这段玩具代码就变成了生产级 Agent 的骨架。框架会换，这个循环不会。

2.3 循环的三个常见故障

问题原因修复方式
原地打转，反复调同一个工具工具结果没写进上下文，模型每轮都以为「还没做」把完整结果（含错误）回灌上下文；记录已尝试动作
越跑越慢、后面开始忘事上下文被工具输出撑爆，早期信息被截断压缩历史、只保留摘要；把大块数据留在工具侧（见 Skill 的脚本）
提前宣布完成模型对「完成」的判断没有依据用可执行校验（测试、断言、文件比对）代替模型自评

三、Skill：给 Agent 看的「岗位手册」

3.1 一个技能就是一个文件夹

Skill 的格式刻意做得极简——一个目录，核心是一个带 YAML 头部的 SKILL.md：

my-skill/
├── SKILL.md          # 必需：元数据 + 操作指令
├── scripts/          # 可选：可执行代码（确定性、不占上下文）
├── references/       # 可选：详细文档，用到才读
└── assets/           # 可选：模板、素材

SKILL.md 开头是这样一段元数据（这就是本仓库 src/SKILL.md 的真实写法）：

---
name: rust-playground
description: 将Rust代码发送到Rust Playground进行评估并返回执行结果
---

name 和 description 是必填的。description 是整个技能最关键的字段——Agent 在启动时只能看到它，靠它判断「这个任务要不要翻这本手册」。描述写得太笼统，技能就永远不会被触发；写得足够具体（包含触发场景和关键词），才会被正确选中。

3.2 渐进式披露：省上下文的核心机关

如果有几十个技能，把它们的全部内容一开局就塞进上下文，窗口立刻爆掉。Skill 的解法是渐进式披露（progressive disclosure），分三层加载：

层级加载时机内容大致体积
第一层：发现启动时，常驻每个技能的 name + description~50 token / 个
第二层：激活任务匹配时完整 SKILL.md 正文~500 token / 个
第三层：执行真正需要时references/ 文档、scripts/ 脚本数千 token，或干脆不进上下文

这像一本组织良好的手册：先看目录（元数据），翻到相关章节（SKILL.md），必要时才去查附录（参考文档）。好处是可挂载的技能数量几乎不受上下文限制，而且技能之间可以自由组合。

脚本这一层尤其巧妙：「把列表排序」用模型逐 token 生成，又贵又不可靠；直接跑一段排序代码，又快又确定。训练和文档可以进上下文，可执行代码只需被调用——这也解释了为什么 Skill 适合装「流程 + 脚本」，而不是装一大段背景知识。

3.3 技能到底是哪种「知识」

有四种容易混淆的东西，官方给过一个很实用的区分：

形态回答的问题特性类比
Prompt「这次临时注意什么」即时、一次性、被动口头交代一句
Project 知识库「关于这个主题该知道什么」静态、始终加载放在工位上的资料夹
Skill「这类活该怎么干」程序性、按需激活、跨会话持久员工培训手册
Subagent「谁能独立把这件事做完」有自己的上下文和工具权限一个专职同事

一句话记忆：Project 说「这是你需要知道的」，Skill 说「这是做事的步骤」。 而且它们可以叠加：一个专职 Subagent 完全可以调用 Skill 来获得某个领域的规范做法。

Agent Skills 最初由 Anthropic 开发，2025 年末作为开放标准发布（规范在 github.com/agentskills/agentskills），随后被 OpenAI Codex、Cursor、GitHub Copilot、Gemini CLI 等一大批产品采纳。SKILL.md 这个格式本身，成了跨产品通用的「技能普通话」。

四、MCP：AI 应用的 USB-C

4.1 它解决的到底是什么问题

假设有 M 个 AI 应用、N 个外部系统。没有标准协议时，每家都要为每家写适配，工作量是 M × N：

flowchart LR
    subgraph B[没有 MCP：M × N 条专线]
        direction LR
        A1[App 1] --- D1[数据源 1]
        A1 --- D2[数据源 2]
        A2[App 2] --- D1
        A2 --- D2
        A3[App 3] --- D1
        A3 --- D2
    end

MCP 把这个乘法变成加法 M + N：每个应用实现一个客户端，每个系统实现一个服务端，中间用统一协议对话。官方的类比是 USB-C——接口统一后，设备随便插。

flowchart LR
    subgraph C[有了 MCP：M + N 个插头]
        direction LR
        B1[App 1] --- H((MCP))
        B2[App 2] --- H
        B3[App 3] --- H
        H --- E1[数据源 1]
        H --- E2[数据源 2]
    end

4.2 三方角色：Host、Client、Server

MCP 采用客户端—服务端架构，但要区分三个角色，这是最容易搞混的地方：

角色是谁职责
Host（宿主）AI 应用本身，如 Claude Code、VS Code协调全局，为每个服务端创建一个客户端
Client（客户端）Host 内部的组件与某个服务端维持一条专用连接，把上下文取回来
Server（服务端）提供上下文的程序暴露工具、资源、提示词；可本地可远程

关键点：Server 指的是「提供上下文的那个程序」，与它运行在哪里无关。 用 stdio 传输时它跑在本机（本地服务器），用 Streamable HTTP 时它跑在远端（远程服务器）。VS Code 连 Sentry 和本地文件系统，就是两个客户端对两个服务端。

4.3 两层协议：JSON-RPC + 传输

MCP 分两层，理解这个分层，就不会被「它到底用 HTTP 还是 stdio」绕晕：

  • 数据层（内层）：基于 JSON-RPC 2.0，定义消息结构和语义——能力发现、工具/资源/提示词、通知等。这层与传输无关。
  • 传输层（外层）：定义消息怎么送。目前两种：
    • stdio：本地进程的标准输入输出，无网络开销，通常一对一；
    • Streamable HTTP：单个 HTTP 端点收 POST，可用 SSE 流式回传，支持远程和一对多，推荐用 OAuth 认证。

数据层给服务端定义了三个核心「原语」（客户端用它来发现和执行）：

原语是什么谁控制例子
Tools 工具可被模型调用执行动作的函数模型决定调用读写文件、查库、发请求
Resources 资源提供上下文数据的数据源应用决定加载文件内容、数据库记录
Prompts 提示词可复用的交互模板用户决定使用系统提示、少样本示例

每个原语都有对应的发现方法（tools/list、resources/list……），执行用 tools/call。这个「先列表、后调用」的设计让工具清单可以是动态的。客户端还可以反向提供 elicitation（向用户追问信息）等能力。

一个最小的 tools/list 请求与响应长这样（就是纯 JSON-RPC 2.0）：

// 请求
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [{
      "name": "add",
      "description": "两数相加",
      "inputSchema": {"type":"object",
        "properties":{"a":{"type":"number"},"b":{"type":"number"}}}
    }]
  }
}

4.4 版本演进：这条协议还在快速长大

MCP 由 Anthropic 于 2024 年 11 月开源，主要版本节点：

版本关键变化
2024-11-05初版，远程传输用 HTTP + SSE
2025-03-26引入 Streamable HTTP 取代 HTTP + SSE；加入工具注解等
2026-07-28Streamable HTTP 移除 GET 流端点与协议层会话；引入多轮往返请求（MRTR）；sampling 弃用，建议直接对接模型 API

顺带两句安全现实：服务端必须校验 Origin 头以防 DNS 重绑定攻击，本地运行应只绑定 127.0.0.1；MCP 只管「上下文怎么交换」，不管「应用怎么用模型」——把鉴权、权限、审计留给了实现者。这也是为什么「给智能体接一个来路不明的 MCP 服务器」在今天就相当于「给陌生人一把家门钥匙」。

4.5 零依赖 Rust：手搓一个玩具 MCP 服务端

真实的 MCP 开发请用官方 SDK。但为了看懂协议本质，下面只用标准库，手动拼 JSON 字符串，实现一个能回应 initialize 和 tools/list 的 stdio 服务端骨架。Playground 可直接运行——它演示的是协议形状，不是生产实现。

▶ 在 Rust Explorer 中运行
use std::io::{self, BufRead, Write};

// 最简实现：真项目请用 serde + 官方 SDK，别手拼 JSON
fn handle(line: &str) -> String {
    // 只看方法名，忽略其余字段（玩具版）
    if line.contains("\"tools/list\"") {
        r#"{"jsonrpc":"2.0","id":1,"result":{"tools":[
            {"name":"add","description":"两数相加","inputSchema":{"type":"object"}}
        ]}}"#
        .to_string()
    } else if line.contains("\"initialize\"") {
        r#"{"jsonrpc":"2.0","id":1,"result":{
            "protocolVersion":"2026-07-28",
            "capabilities":{"tools":{}},
            "serverInfo":{"name":"toy-mcp","version":"0.1.0"}
        }}"#
        .to_string()
    } else {
        r#"{"jsonrpc":"2.0","id":1,"error":{"code":-32601,"message":"Method not found"}}"#
            .to_string()
    }
}

fn main() {
    let stdin = io::stdin();
    let stdout = io::stdout();
    let mut out = stdout.lock();

    // stdio 传输：一行一个 JSON-RPC 消息
    for line in stdin.lock().lines() {
        let request = line.unwrap_or_default();
        if request.trim().is_empty() {
            continue;
        }
        let response = handle(&request);
        writeln!(out, "{response}").expect("写响应失败");
        out.flush().expect("刷新失败");
    }
}
# 手测：把两行 JSON 喂给程序，看它怎么回
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  | cargo run --quiet

Host 启动时正是这样拉起服务端、握手、列工具，然后把工具清单交给模型——接下来就轮到 Agent 的循环上场了。

五、串起来：一句话需求是怎么被完成的

回到开头那个「填 PDF + 写周报」。三件套协同的完整时序是：

sequenceDiagram
    participant U as 用户
    participant A as Agent（LLM + 循环）
    participant S as Skill（填表手册）
    participant M as MCP Client→Server

    U->>A: 填好 invoice.pdf 并整理周报
    A->>A: 扫描技能元数据，命中「PDF 表单」技能
    A->>S: 读取 SKILL.md（第二层）
    S-->>A: 流程：读字段→逐项填→校验→套模板
    Note over A,S: 需要表单细节时，再读 references/forms.md（第三层）
    A->>M: tools/list 发现可用工具
    M-->>A: 工具清单（读 PDF、写文件、发邮件…）
    loop Agent 循环
        A->>M: tools/call 读表单字段
        M-->>A: 字段列表
        A->>A: 按手册填写、校验
    end
    A->>M: tools/call 写出周报文件
    M-->>A: 写入成功
    A-->>U: 完成，文件在 ./weekly.md

注意三条线各司其职：

  • Skill 那条线给的是方法——「填表要先读字段再套模板」；
  • MCP 那条线给的是能力——「这里有读 PDF、写文件这些工具」；
  • Agent 那条线把它们编排成循环——「现在该读手册了」「现在该调工具了」「校验通过，收工」。

这也是三者最容易被误解的地方：MCP 不替你思考，Skill 不替你动手，Agent 不凭空知道行业知识。 它们拼起来才是一个完整的「员工」。

六、踩坑指南

问题原因修复方式
技能写好了却从不被触发description 太抽象，Agent 匹配不上在描述里写清触发场景、关键词和「何时不该用」
挂了很多技能后变笨变慢第一层元数据过多，或一上来就加载全部正文遵循三层披露；正文只放流程，细节移入 references/
接了 MCP 后工具太多，模型选错一堆功能相近的工具同时出现在上下文收敛工具数量、写清描述；用 tools/list 动态暴露子集
Agent 反复调用同一个工具工具报错信息没回灌，模型以为没执行把结构化错误写回上下文，并设置最大轮次与去重
安全隐患：数据外泄或误操作来路不明的 MCP 服务端、权限过大、无人在环只接可信服务端；最小权限；敏感动作走 elicitation 让用户确认

七、结语

这一附录想留下的，不是三个名词，而是一个拆解问题的框架：

当智能体干不好活时，先别急着换模型。问三句——它有没有一个会收敛的循环（Agent）？有没有正确的做事方法（Skill）？有没有够得着工具的手脚（MCP）？

工程上绝大多数「AI 不够聪明」的抱怨，拆开来看，都是这三样里某一件没到位。而这三样恰好都不是模型问题——它们是可以被设计、被审查、被版本管理的工程问题。

从这个角度看，2025—2026 年真正的变化，不是模型突然更聪明了，而是我们终于学会了怎么给聪明模型配上手册和插座。
